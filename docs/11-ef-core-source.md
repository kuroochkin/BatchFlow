# Пакетное чтение через DbContext

[Оглавление](README.md) · [Контексты и собственные источники EF Core](10-entity-framework-core.md)

## Назначение и границы

`EfCoreBatchSource<TContext, TItem, TCheckpoint>` выполняет keyset-чтение через EF Core без собственного наследника source. Приложение задает выборку и смысл позиции; адаптер строит запрос порции, материализует данные и освобождает контекст. Очередь, параллелизм обработчиков, retry, события и сохранение checkpoint остаются в стандартном runtime.

Источник реализует `IBatchSource` напрямую, а не наследует `EntityFrameworkCoreBatchSourceBase`: у старого базового класса контекст живет одно перечисление, у готового источника - только одну порцию. Поведение и сигнатуры базового класса сохранены для совместимости.

Пакет использует EF Core 9.0.15 и `net9.0`, не выбирает провайдер БД и не зависит от `BatchFlow.Postgres`. Приложение устанавливает и настраивает совместимый EF-провайдер. EF-хранилища контрольных точек в пакете нет: используйте любой существующий `ICheckpointStore<TCheckpoint>`.

## Быстрый старт

Полный исполняемый пример с SQLite в памяти находится в [samples/BatchFlow.EntityFrameworkCore.Sample](../samples/BatchFlow.EntityFrameworkCore.Sample/Program.cs). Он не требует внешней БД и не изменяет постоянные данные:

```sh
dotnet run --project samples/BatchFlow.EntityFrameworkCore.Sample
```

Первый запуск обрабатывает три заказа и сохраняет позицию `3`. Второй запуск того же job и store начинает с `3`, не обрабатывает заказы повторно и возвращает `Succeeded`. In-memory store сохраняет состояние только в текущем процессе.

Основная конфигурация из примера, где `factory` - настроенный `IDbContextFactory<OrdersDbContext>`, а `OrderDto` - модель с `Id` и `Number`:

```csharp
var sourceOptions = new EfCoreBatchSourceOptions<OrdersDbContext, OrderDto, long>
{
    Context = EntityFrameworkCoreContextOptions<OrdersDbContext>.FromDbContextFactory(factory),
    QueryFactory = db => db.Orders.Where(order => order.ExportReady)
        .Select(order => new OrderDto { Id = order.Id, Number = order.Number }),
    ApplyStableOrdering = query => query.OrderBy(order => order.Id),
    ResumePredicateFactory = checkpoint => order => order.Id > checkpoint,
    CheckpointSelector = order => order.Id,
    CheckpointComparer = Comparer<long>.Default,
};
```

Options передаются прямо в `.FromEntityFrameworkCore(sourceOptions)`. Также можно создать `new EfCoreBatchSource<OrdersDbContext, OrderDto, long>(sourceOptions)` и передать его в `.FromEntityFrameworkCore(source)` или обычный `.From(source)`. Во всех вариантах запросы начинаются только при запуске и чтении перечислителя. Полный пример показывает builder, обработчик и обязательную проверку `summary.Status`.

## Контракт options

Все шесть свойств обязательны; пропуск проверяет компилятор, явный `null` отклоняет конструктор:

| Свойство | Ответственность приложения | Что делает адаптер |
| --- | --- | --- |
| `Context` | Фабрика отдельного контекста на каждое обращение | Вызывает фабрику на порцию и освобождает контекст до выдачи пакета |
| `QueryFactory` | Отложенный `IQueryable<TItem>` из предоставленного контекста, фильтры и при необходимости DTO-проекция | Проверяет провайдер и основную цепочку, не выполняет клиентскую пагинацию |
| `ApplyStableOrdering` | Один `OrderBy`/`OrderByDescending` и дополнительные `ThenBy`/`ThenByDescending` | Проверяет, что сортировка продолжает переданный запрос, а не отбрасывает checkpoint-фильтр |
| `ResumePredicateFactory` | `Expression<Func<TItem, bool>>`, обозначающий строгое продолжение | Сам применяет `Where` только при наличии позиции |
| `CheckpointSelector` | Чистое извлечение неизменяемого checkpoint из материализованного элемента | Использует checkpoint последнего элемента, выданного в пакете, а не дополнительной строки |
| `CheckpointComparer` | Сравнение в том же полном порядке, что и в БД | Проверяет строгое продвижение каждой позиции, включая сохраненную границу и дополнительную строку |

Фильтр продолжения передается как expression, а не как делегат, принимающий весь запрос. Поэтому он не может незаметно подменить источник, добавить `Skip` или изменить сортировку. Адаптер не вызывает `Compile` для SQL-предиката и не переключается на LINQ to Objects.

`TItem` - ссылочный тип сущности или DTO; скалярные значения и структуры следует оборачивать в ссылочную модель результата. `TCheckpoint` может быть структурой или классом, но не `null`. Нулевой и отрицательный числовой checkpoint допустимы: отсутствие позиции определяется наличием `ResumeFrom`, а не значением `default`.

## Короткое время жизни контекста

Одна порция проходит следующие шаги:

1. Runtime разрешает очередное чтение с учетом своего ограниченного окна.
2. Источник получает контекст из фабрики и отключает tracking по умолчанию и lazy loading в этом контексте.
3. `QueryFactory` строит запрос; при наличии позиции добавляется `Where` с предикатом продолжения.
4. Добавляются стабильная сортировка, `AsNoTracking` и `Take(RequestedBatchSize + 1)`.
5. Запрос полностью материализуется; проверяются элементы и позиции.
6. Дополнительный элемент удаляется, контекст освобождается, проверяется отмена.
7. Только после этого готовый пакет выдается runtime. Следующее чтение получает отдельную аренду контекста.

`RequestedBatchSize` должен быть от `1` до `Int32.MaxValue - 1`; последнее ограничение связано с дополнительным элементом. Размер выдаваемого пакета не превышает запрошенного. Если данных нет, последовательность заканчивается без пустого пакета. При неполной последней порции дополнительный запрос не выполняется.

`IDbContextFactory` и `PooledDbContextFactory` - рекомендуемые способы подключения. Пользовательские синхронная и асинхронная фабрики из `EntityFrameworkCoreContextOptions` тоже поддерживаются. Фабрика с пулом может выдавать тот же физический объект повторно, но между порциями он возвращается в пул. Самой фабрикой продолжает владеть приложение.

Готовый внешний контекст из `FromContext` отклоняется конструктором этого источника. Нельзя гарантировать короткую аренду, повторные запуски и безопасное освобождение, если адаптер получил общий scoped-контекст приложения. Для специальных источников с внешним владением остается старый базовый класс, описанный в [отдельном руководстве](10-entity-framework-core.md).

Обработчики не получают контекст чтения. Для записи или дополнительных запросов используйте отдельную фабрику/контекст в обработчике, учитывая DOP и границу своей транзакции. Вызов `SaveChanges` не выполняется автоматически.

Курсор хранится отдельно для каждого перечисления source. Один экземпляр можно использовать для независимых запусков, если фабрика, делегаты конфигурации и сравниватель безопасны при параллельных вызовах; адаптер не синхронизирует их пользовательское состояние. Совместный checkpoint store с одним идентификатором не является блокировкой одновременного запуска job.

## Полный и детерминированный порядок

Уникальный стабильный порядок обязателен даже без постоянного checkpoint store: он нужен для перехода между порциями одного запуска. Например, сортировки только по дате недостаточно, если даты повторяются. Добавьте уникальный `Id` через `ThenBy`, включите оба значения в checkpoint, предикат и сравниватель.

Для порядка `Bucket DESC, Id ASC` нужны согласованные правила:

- Сортировка: `query.OrderByDescending(row => row.Bucket).ThenBy(row => row.Id)`.
- Позиция: неизменяемая запись с `Bucket` и `Id`.
- Продолжение: `row.Bucket < checkpoint.Bucket || (row.Bucket == checkpoint.Bucket && row.Id > checkpoint.Id)`.
- Сравнение: сначала `right.Bucket.CompareTo(left.Bucket)`, при равенстве - `left.Id.CompareTo(right.Id)`.

Для допустимого перехода `Compare(previous, next)` всегда меньше нуля. Источник не подбирает сравниватель автоматически: порядок строк зависит от collation, а порядок GUID и других типов может отличаться между .NET и конкретной БД. Nullable-ключи требуют явно определенного полного порядка и checkpoint, отличного от `null`; нельзя полагаться на неявный порядок `NULL`.

Читается одна дополнительная строка, потому что проверка только внутри пакета не обнаружила бы одинаковые позиции по разные стороны его границы, особенно при batch size `1`. Ошибка обнаруживается до выдачи такого пакета и до его подтверждения. Дополнительная строка не кешируется для следующей порции: она читается заново в новом контексте. `CheckpointSelector` должен быть чистым и не зависеть от числа вызовов.

Эта проверка не доказывает уникальность всей выборки и не заменяет ограничения/индексы схемы. Уникальность полного ключа, неизменяемость ключей и соответствие предиката бизнес-выборке остаются обязанностью приложения. Для эффективного keyset-чтения проверьте индекс по фильтрам и полному набору ключей на плане запроса своей БД.

## Ограничения запросов

- В основной LINQ-цепочке `QueryFactory` запрещены `Skip`, `Take`, `SkipLast`, `TakeLast` и `Reverse`. Порцию ограничивает сам источник; бизнес-подзапросы внутри фильтров могут иметь собственные ограничения.
- `ApplyStableOrdering` добавляет только один первичный `OrderBy` и цепочку `ThenBy`. Нельзя игнорировать вход, добавлять `Where` или другую пагинацию, повторять первичный `OrderBy`. Фильтры и проекции размещаются в `QueryFactory`.
- Запрос должен использовать штатный EF-провайдер текущего контекста. Захваченный `IQueryable` из другого контекста, `AsQueryable` поверх коллекции и сторонние обертки, заменяющие провайдер, не поддерживаются.
- Фильтры, сортировка и продолжение должны транслироваться в SQL/язык провайдера. Для DTO используйте проекции, допускающие дальнейшее построение запроса, например инициализатор свойств из примера. Позиционный конструктор DTO не всегда поддерживает последующие `Where`/`OrderBy`. Ошибка трансляции не вызывает загрузку всей таблицы в память.
- Не выдавайте `IQueryable`, ленивые навигации, прокси lazy loading или связанные с живым контекстом модели. Предпочтительна явная DTO-проекция. `Include`, auto-includes и большие графы могут увеличивать память и число SQL-команд: ограничение числа элементов не ограничивает объем их графов в байтах.
- Проверка LINQ не является SQL-парсером. Нельзя скрывать offset, нестабильную сортировку или зависящую от времени пагинацию внутри пользовательского raw SQL.

Адаптер не меняет настройки таймаута провайдера, не добавляет миграции и не обещает ровно одну SQL-команду: EF execution strategy, split queries и конфигурация провайдера могут влиять на выполнение. Эти параметры настраиваются в приложении.

## Resume и изменяющиеся данные

Checkpoint означает «последняя подтвержденная позиция», а не снимок БД и не номер страницы. Источник начинает строго после нее. Retry обработчика не является retry чтения или сохранения checkpoint; повтор после сбоя может снова затронуть уже выполненные внешние операции. Обработчик должен быть идемпотентным.

Каждая порция читает через отдельный контекст. Общей snapshot-транзакции на job нет. Удаление строки после предварительного чтения, изменение фильтра или ключа и новые записи между порциями влияют на выборку. Поздний коммит с ключом ниже уже подтвержденного checkpoint может не попасть в последующие запуски. Монотонный sequence/identity сам по себе не задает порядок коммитов.

Если нужен фиксированный набор, приложение должно подготовить неизменяемый список/снимок или обоснованную стратегию согласованности и верхнюю границу. Верхняя граница помогает ограничить объем job, но сама по себе не устраняет поздние коммиты. Источник не является подпиской на постоянно растущую таблицу и завершает чтение, когда очередная выборка исчерпана.

Фильтры арендатора, временные границы и прочие параметры фиксируйте на запуск и согласуйте с checkpoint при восстановлении. Не меняйте их через `DateTime.UtcNow` внутри каждой `QueryFactory`. При изменении смысла запроса, ключей, сортировки или формата checkpoint используйте новый `CheckpointId` либо явную миграцию прогресса. Не разделяйте один поток checkpoint между арендаторами.

## Ошибки и отмена

Ошибки настройки обязательных полей и внешний контекст отклоняются при создании source. Форма конкретного запроса, SQL-трансляция и монотонность проверяются при чтении; при обычном запуске runtime отражает такой сбой в `summary.Status == Failed` и `summary.Exception`.

Отмена передается в создание контекста и асинхронное выполнение запроса. Она проверяется также при валидации элементов и после завершения `DisposeAsync`, до выдачи пакета. Источник не возвращает пакет, пока освобождение контекста не завершилось. Если освобождение само упало после успешного чтения, пакет также не выдается.

Первичная ошибка запроса, извлечения/сравнения checkpoint или отмена не подменяется вторичной ошибкой освобождения контекста. Если при успешном чтении отмена пришла во время `DisposeAsync`, а освобождение тоже завершилось ошибкой, возвращается `OperationCanceledException` с основным токеном; ошибка очистки доступна в `InnerException`. Уже возникшая ошибка чтения сохраняет приоритет над последующей отменой. Самостоятельная ошибка освобождения без отмены не скрывается. Отмена кооперативная: конкретный драйвер может не прерывать SQL немедленно, а `DisposeAsync` не имеет токена отмены. Приложение должно проверять итоговый summary, а не только отсутствие исключения.

## Проверка и self-review

Постоянные проверки используют настоящий SQLite и отдельные контексты/соединения в именованной БД в памяти. Они покрывают размер и SQL-лимит порций, отсутствие OFFSET в сформированном запросе, ascending/descending/составные checkpoint, restart, DTO, отсутствие tracking, дубликаты на границе, некорректные запросы, пул, два одновременных перечисления, отмену и первичные ошибки.

Первый проход self-review добавил регрессии для отмены в последнем `CheckpointSelector` и в `DisposeAsync`; обнаруженная выдача пакета после отмены исправлена финальной проверкой токена. Второй проход проверил изоляцию курсоров, обязательность сортировки, возврат аренды на каждую порцию и восстановление настроек EF после пула. Перекрестные регрессии выявили подмену отмены ошибкой очистки на границе порции: добавлены проверка до начала очистки и явный приоритет отмены при сбое `DisposeAsync`. Ограничения DTO-трансляции зафиксированы без клиентского обхода пагинации.

```sh
dotnet test tests/BatchFlow.EntityFrameworkCore.Tests/BatchFlow.EntityFrameworkCore.Tests.csproj
```

SQLite не доказывает идентичное поведение PostgreSQL, SQL Server, Cosmos DB, их collation, типов и изоляции. Перед эксплуатацией запрос, сравниватель, индексы, отмену и resume следует проверить на выбранном провайдере и реальной схеме. Эти тесты не являются нагрузочным benchmark и не доказывают exactly-once.
