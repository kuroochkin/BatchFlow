# Контрольные точки и восстановление

[Оглавление](README.md) · [Далее: ошибки и отмена](03-errors-and-cancellation.md)

## Что подтверждает checkpoint

Контрольная точка означает, что все пакеты до этой границы достигли окончательного исхода: успеха или разрешенного пропуска. Она сохраняется после обработки целого пакета. Успех одного элемента внутри незавершенного пакета checkpoint не продвигает.

Обычный запуск выполняет следующие действия:

1. Загружает checkpoint по идентификатору.
2. Передает его в `BatchSourceContext.ResumeFrom`.
3. Получает от source пакет и следующую позицию.
4. Обрабатывает все элементы пакета.
5. Сохраняет подтвержденную позицию и новый токен конкуренции.

Если приложение упало после внешней бизнес-операции, но до сохранения checkpoint, операция может выполниться повторно. При корректном source и постоянном store это модель с возможными повторными доставками, обычно называемая at-least-once. Библиотека не делает общую транзакцию для source, назначения и checkpoint и не обещает exactly-once.

## Подключение хранилища

Фрагмент продолжает пример из README:

```csharp
var store = new BatchFlow.Checkpoints.InMemoryCheckpointStore<long>();

var job = BatchJob
    .Named("orders-export")
    .From(source)
    .WithCheckpoint("orders-export-v1", store)
    .ProcessEach((_, _, _) => ValueTask.CompletedTask)
    .Build();

var firstRun = await job.RunAsync();
var secondRun = await job.RunAsync();
```

При повторном запуске source из README исключит уже подтвержденные заказы. В этом примере нужен тот же экземпляр `store`: новый in-memory store не знает о предыдущем запуске.

Перегрузка `.WithCheckpoint(store)` использует имя задачи как checkpoint ID. Явный стабильный ID удобнее, если отображаемое имя задачи меняется. `RunId` обозначает один запуск и не участвует в поиске checkpoint.

При изменении фильтра, порядка обхода или смысла checkpoint заведите новый ID либо проведите явную миграцию состояния. Иначе старая позиция может пропустить нужные данные.

## Какие источники поддерживают resume

`IBatchSource<TItem, TCheckpoint>` по умолчанию сообщает `SupportsResume = true`; реализатор обязан действительно учитывать `context.ResumeFrom`. Само наличие типизированного checkpoint не делает источник возобновляемым.

`IBatchSource<TItem>` использует `NoCheckpoint` и сообщает, что resume недоступен. Для него fluent API не предлагает `WithCheckpoint`. Приведение к общему generic-интерфейсу не обходит runtime-валидацию: store для невозобновляемого source будет отклонен.

Возобновляемый source можно запустить без store. Он будет двигать свою позицию в пределах чтения, но следующий запуск начнется без сохраненного checkpoint.

## Из чего состоит сохраненная точка

| Поле | Назначение |
| --- | --- |
| `Value` | Позиция, которую понимает source |
| `SequenceNumber` | Номер пакета в том запуске, где точку сохранили |
| `ConcurrencyToken` | Версия записи для оптимистичной конкуренции |
| `SavedAt` | Время сохранения |
| `Metadata` | Метаданные source для подтвержденного пакета |

`SequenceNumber` начинается заново в следующем запуске. Это не глобальный номер записи и не замена `Value`. Для пагинации используйте значение checkpoint, например ID или пару `(created_at, id)`.

`InMemoryCheckpointStore` копирует словарь метаданных, но не выполняет глубокое копирование `Value`. Для checkpoint предпочтительны неизменяемые значения и records.

## Подтверждение при параллельной batch-обработке

Если пакет `2` завершился раньше `1`, coordinator запоминает его, но не сохраняет checkpoint `2`. Когда завершится `1`, подтверждает непрерывную последовательность `1`, `2`. Пакет за границей ошибки не может продвинуть checkpoint через незавершенный пакет.

Это защищает границу восстановления, но не отменяет внешние эффекты более поздних пакетов. После сбоя такие пакеты могут быть прочитаны и обработаны повторно.

Сейчас coordinator хранит ожидающие пакеты целиком, а размер окна не ограничен. Очень долгий первый пакет при быстрых следующих способен накопить большой объем данных. Входной `PrefetchCapacity` не устраняет этот риск; см. [разбор проекта](08-review.md).

## Пропуски и конкуренция

Разрешенный `Skip` учитывается как окончательный исход и позволяет сохранить checkpoint. При следующем запуске пропущенный элемент автоматически не вернется. Для отдельной очереди повторной обработки нужно записывать проблему самостоятельно; готового dead-letter хранилища пока нет.

`SaveAsync` принимает `expectedConcurrencyToken`, полученный из предыдущей загрузки или сохранения. Store должен атомарно отклонять устаревшую запись через `CheckpointConflictException`. Runtime завершает такой запуск с `Failed`; конфликт не проходит через retry обработчика.

Оптимистичная конкуренция защищает запись прогресса, но не блокирует два обработчика до выполнения бизнес-операций. Для запрета одновременных запусков одного задания нужен lock/lease на уровне приложения или отдельный механизм распределенной координации.

## Постоянное хранилище

Для восстановления между процессами используйте `PostgresCheckpointStore<TCheckpoint>` или собственную реализацию `ICheckpointStore<TCheckpoint>`. PostgreSQL-store можно использовать с любым совместимым source, а PostgreSQL-source - с любым совместимым store: совпадать должен тип `TCheckpoint`.

Создание таблицы PostgreSQL выполняется явно через `EnsureStorageAsync` либо миграцию приложения. Подробности в [PostgreSQL-руководстве](04-postgres.md).
