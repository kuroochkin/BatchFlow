# Публичные NuGet-пакеты BatchFlowKit

[Оглавление](README.md) · [Семейство пакетов](../eng/nuget/README.md)

## Имена и статус

Публичное имя - **BatchFlowKit**, лицензия - [MIT](../LICENSE).
Исходные проекты, DLL и C#-пространства имен сохраняют `BatchFlow`:
`BatchFlowKit.Postgres` устанавливает `BatchFlow.Postgres.dll`, код использует
`using BatchFlow.Postgres...`. Пакет `BatchFlow` в NuGet.org принадлежит другому
проекту; его нельзя использовать вместо нашего фасада.

Версия кандидата: `0.1.0-preview.1`. До успешной загрузки и индексации в
NuGet.org она **не считается опубликованной**. HTTP 404 в каталоге не
гарантирует отсутствие резервирования имени.

Упаковываются десять готовых библиотек. Diagnostics, консольный пример,
samples, тесты и инструменты `eng` не являются публикуемыми пакетами.
Проект явно включает `IsBatchFlowPackage`, общие метаданные задаются в
`Directory.Build.targets`; по умолчанию `IsPackable=false`.

`Directory.Build.props` задает единую версию. NuGet-зависимости между своими
пакетами используют новые ID и ту же версию; DLL не копируются в фасад.
В каждый архив входят README, MIT и XML; portable PDB отправляются отдельными
`snupkg`, с привязкой Source Link к исходному commit. При обновлении версии
обновляйте также примеры установки, README пакетов и changelog.

## Локальная подготовка

Нужен SDK, совместимый с `global.json`. Из корня репозитория:

```sh
bash eng/pack.sh
```

Скрипт не публикует пакеты. Он восстанавливает зависимости, собирает Release,
запускает тесты solution, упаковывает библиотеки и проверяет содержимое.
Затем в пустой временный NuGet-кеш устанавливается приложение-потребитель
без `ProjectReference`: оно проверяет each/batch, retry, resume, события,
logging, реальное чтение EF/SQLite и разрешение DI обоих адаптеров.

Source Mapping разрешает `BatchFlowKit*` только из каталога кандидатов,
остальные зависимости - из NuGet.org. Случайно установленная глобальная
версия не может подменить наш архив. Дополнительно шесть отрицательных
регрессий проверяют сам валидатор: отсутствие лицензии, старое имя или
версия зависимости, пропавший пакет/символы и посторонний архив.

Каталог по умолчанию - `artifacts/packages`. Он должен быть пустым: скрипт
не смешивает старые и новые артефакты и не удаляет файлы пользователя.
Для повторной проверки выберите другой каталог:

```sh
bash eng/pack.sh artifacts/next-candidate
```

Без `BATCHFLOW_POSTGRES_TESTS` SQL-интеграционные тесты явно пропускаются.
Для полной проверки используйте [отдельную тестовую PostgreSQL-БД](../tests/BatchFlow.Postgres.Tests/Integration/README.md).
Тогда скрипт также запустит полный SQL-пример в его собственной временной
схеме. EF-пример запускается всегда. Не используйте БД приложения.

Ручная повторная проверка готового каталога:

```sh
dotnet run --project eng/BatchFlow.PackageValidation -- artifacts/packages 0.1.0-preview.1 --self-test
```

Валидатор проверяет ID, версию, внутренние зависимости, MIT, README, XML,
набор DLL, SHA репозитория и Source Link в PDB. Кандидат из незакоммиченного
рабочего дерева пригоден для локальной проверки, но не является релизом.
Окончательные пакеты workflow пересобирает из проверенного тега.

## Первая публикация

Аккаунт владельца и политика доверия настраиваются человеком, не хранятся
в репозитории. Публикация разрешает загрузку публичных бинарных файлов;
она не меняет видимость GitHub-репозитория.

1. Зарегистрируйтесь на [NuGet.org](https://www.nuget.org/users/account/LogOn), подтвердите почту и защитите учетную запись двухфакторной аутентификацией.
2. После ревью внесите изменения релиза в основную ветку GitHub. Здесь это `master`; workflow публикации запускается только из текущей default branch.
3. В GitHub создайте environment `nuget`. Для публичной поставки рекомендуется настроить обязательное одобрение владельцем и ограничить допустимые ветки основной веткой.
4. По умолчанию workflow использует NuGet-профиль `kuroochkin`. Для другого владельца задайте GitHub Actions Variable `NUGET_USER`: публичное имя профиля NuGet, не email и не API-ключ. При текущем владельце эта переменная не нужна.
5. На NuGet.org создайте Trusted Publishing policy: owner репозитория `kuroochkin`, repository `BatchFlow`, workflow file `publish-nuget.yml`, environment `nuget`. Разрешите новые пакеты и новые версии только семейства `BatchFlowKit*`.
6. Создайте тег `v0.1.0-preview.1` на прошедшем ревью commit основной ветки и отправьте его в GitHub. После этого вручную запустите workflow «Публикация BatchFlowKit в NuGet.org», выбрав основную ветку и указав этот тег.

Поля политики соответствуют [документации Trusted Publishing](https://learn.microsoft.com/en-us/nuget/nuget-org/trusted-publishing).
Этот способ получает краткоживущий ключ через OIDC; постоянный API-ключ не
нужен. Не передавайте пароль/ключ в чат и не записывайте их в NuGet.Config.

Workflow сначала проверяет, что тег существует, соответствует версии и
принадлежит истории основной ветки. Затем выполняет весь `eng/pack.sh`,
включая реальные PostgreSQL-тесты в отдельном CI-сервисе. Только после успеха
другой job скачивает **те же проверенные архивы** и получает право публикации
в environment `nuget`. Действия GitHub закреплены полными SHA; проверочный
job не получает `id-token: write`.

Пакеты отправляются в порядке зависимостей: Abstractions, Core, фасад,
расширения и адаптеры. `dotnet nuget push` также отправляет соседний `snupkg`.
Групповой транзакции NuGet нет: при частичном сбое повторите тот же workflow.
`--skip-duplicate` позволяет пропустить уже загруженные версии, но не заменить
их содержимое. Если в выпущенной версии найден дефект, нужна **новая версия**.

Первая настройка policy и запуск workflow не проверены локальной сборкой:
они требуют существующего NuGet-профиля, доступа к GitHub и настроек владельца.
Окончательное подтверждение публикации - успешный workflow и доступность
всех десяти точных ID/версий через NuGet.org, а не только наличие артефактов
GitHub. Для отладки по Source Link исходный commit должен быть доступен
потребителю; приватный репозиторий автоматически публичным не становится.

## Установка после публикации

После индексации версии:

```sh
dotnet add package BatchFlowKit --version 0.1.0-preview.1
```

При необходимости отдельно добавьте `BatchFlowKit.Postgres`,
`BatchFlowKit.EntityFrameworkCore`, logging или соответствующий DI-пакет.
В менеджере пакетов включите отображение предварительных версий.

В Niti на первом этапе достаточно `BatchFlowKit`: SQL outbox и транзакция
`FOR UPDATE SKIP LOCKED` остаются в Niti, библиотека ограничивает обработку
уже выбранной партии. Keyset-checkpoint нельзя использовать вместо статусов
outbox, а runtime-retry нельзя неявно смешивать с долговечным `AttemptCount`.
Фактическое подключение Niti - отдельный шаг после доступности пакетов.
