# Надежность runtime и PostgreSQL

[Оглавление](README.md) · [Исторический разбор](08-review.md)

## Исправленные инварианты

Общее окно пакетов ограничено от резервирования места перед чтением до подтверждения результата. В batch-режиме лимит равен `PrefetchCapacity + DegreeOfParallelism`, в item-режиме - `PrefetchCapacity + 1`. Ограничены и входная очередь, и очередь уведомлений workers. Завершение позднего пакета не освобождает место до сохранения непрерывной последовательности checkpoint. Это исключает накопление всей выборки за долгим первым пакетом, но не ограничивает размер одного элемента в байтах.

Остановка отправляет отмену, ожидает producer и всех workers и только затем возвращает результат. Ошибки source, store и observer проходят через тот же shutdown. Обработчик, игнорирующий отмену, задерживает завершение; движок не оставляет его работать после возврата. Нельзя считать сигнал отмены принудительным завершением пользовательского I/O.

Первичный terminal outcome сохраняется отдельно от вторичных ошибок остановки. Внутренняя отмена ожидающего пакет worker не заменяет ошибку handler. Внешняя отмена после проверки конфигурации возвращает `Cancelled` в summary. Финальные observers вызываются с `CancellationToken.None`; ошибка одного не меняет итог и не препятствует остальным. Медленный observer остается на критическом пути и должен ограничивать собственные внешние операции.

## PostgreSQL

Owned-соединение освобождается при неудачном открытии и отмене без подмены исходного исключения. Готовое `AdapterOwned`-соединение запрещено для checkpoint store; для повторных операций есть строка, data source, фабрика и отдельное открытое External-соединение. Для source AdapterOwned остается режимом одного перечисления.

До обращения к БД проверяются положительный размер пакета, известная модель ownership, пустые и конфликтующие имена стандартных параметров и допустимые флаги reader. Проверка порядка применяется к каждой строке и границе resume. `CheckpointProgressionValidator` позволяет задать возрастание, убывание и составной порядок; произвольный SQL автоматически не анализируется.

Keyset не обеспечивает доставку всех изменений живой таблицы. Поздние коммиты, смена ключа и фильтра требуют выбранного приложением сценария: стабильный набор, управляемый снимок одного запуска, staging для устойчивого resume или CDC/outbox. [Подробный контракт чтения](04-postgres.md).

## Наблюдаемость и совместимость

Добавлены `ProcessingRetryEvent`, `ProcessingSkippedEvent` и `BatchCompletedEvent.Issues`. События не копятся в истории engine, а доставляются observers последовательно в пределах запуска. Событие skip не означает сохранение checkpoint и может повториться после восстановления. Транзакционный error sink не добавлен; при необходимости потребитель сохраняет события во внешней системе.

Все записи logging adapter содержат `RunId`; retry и skip имеют собственные EventId и настраиваемые уровни. Исключения и причины нужно учитывать при настройке маскировки чувствительных данных.

Для потребителей изменилось поведение в четырех местах: отмена стабильно возвращает summary; shutdown ожидает незавершенные handlers; поток observers содержит новые виды событий; некорректные PostgreSQL options отклоняются раньше. Обработчики событий должны учитывать неизвестные будущие типы без падения, а тесты точной последовательности - новые retry/skip.

## Проверки и границы

[RuntimeSafetyTests](../tests/BatchFlow.Core.Tests/Execution/RuntimeSafetyTests.cs) покрывают общее окно, source/store/observer shutdown, первичную ошибку и границы отмены. [ProcessingObservabilityTests](../tests/BatchFlow.Core.Tests/Execution/ProcessingObservabilityTests.cs) покрывают item/batch retry и skip, причины и сериализацию observers. Стресс-проверки обрабатывают 2000 пакетов при нескольких DOP с проверкой лимита и последовательности коммитов.

[Интеграционный набор](../tests/BatchFlow.Postgres.Tests/Integration/README.md) проверяет настоящие SQL, JSONB, время, конкуренцию checkpoint, resume, отмену и возврат соединений в пул на отдельной БД. Он не подменяется fake reader и не объявляется успешным при отсутствии БД: локально без настройки он явно пропускается.

Остаются отдельными задачами benchmark, контролируемый failover/сетевые разрывы, coalescing checkpoint, долговечный error sink, автоматическая модель снимков/CDC и выпуск NuGet/CI/LTS. Эти возможности не следует считать реализованными исправлениями runtime.

Проверка 4 ноября 2026 года: Release-прогон прошел без пропусков, 92 Core-теста и 64 PostgreSQL-теста, из которых 16 интеграционных, на PostgreSQL 17.10. Конкурентные регрессии runtime и событий дополнительно прошли десять повторных прогонов. Сборка solution и 18 C#-примеров документации прошла без предупреждений; примеры без внешней БД выполнены. Это функциональная проверка, не измерение производительности.
