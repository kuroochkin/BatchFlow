# Инструкции для работы с BatchFlow

Эти правила действуют для всего репозитория. При изменениях сохраняй сложившийся стиль и публичные контракты библиотеки. Более конкретные инструкции во вложенных `AGENTS.md`, если они появятся, относятся к соответствующим каталогам.

## Контекст проекта

BatchFlow - библиотека .NET для пакетной обработки с возобновлением по контрольной точке. Приложение предоставляет источник и бизнес-обработчик; runtime управляет чтением, очередью, обработкой, ошибками и подтверждением прогресса.

Перед изменением изучи относящиеся к задаче исходники и тесты. Используй документацию как карту проекта, а фактический код - как источник текущего поведения:

- [README](README.md) - подключение и полный пример запуска.
- [Оглавление документации](docs/README.md) - пользовательские сценарии.
- [Архитектура и стиль](docs/07-architecture-and-style.md) - слои и порядок изучения.
- [Разбор проекта](docs/08-review.md) - исторические дефекты и кандидаты на оптимизацию; актуальный статус исправлений описан в [надежности runtime](docs/09-runtime-hardening.md).
- `docs/batchflow-grooming.md` - исторические планы, а не спецификация реализованного API.

Версии SDK и общие настройки бери из `global.json` и `Directory.Build.props`. Сейчас проекты используют `net9.0`, nullable, implicit usings и генерацию XML-документации. Обновление платформы или зависимостей не включай в несвязанную задачу.

## Границы архитектуры

| Проект | Ответственность |
| --- | --- |
| `BatchFlow.Abstractions` | Минимальные интерфейсы, контексты, результаты, события и модели ошибок; без зависимостей от других проектов |
| `BatchFlow.Core` | Execution engine, очереди, workers и checkpoint coordinator; зависит только от `Abstractions` |
| `BatchFlow` | Публичный фасад, fluent builder, запуск, встроенные политики и in-memory store |
| `BatchFlow.Postgres` | SQL-чтение, Npgsql, подключения, материализация и PostgreSQL checkpoint store |
| `BatchFlow.EntityFrameworkCore` | LINQ/keyset-source, получение и жизненный цикл `DbContext`; без конкретного провайдера |
| `BatchFlow.Extensions.Logging` | Адаптация runtime-событий в `ILogger` |
| `BatchFlow.Testing` | Тестовые реализации и фиксация вызовов |

`Extensions.DependencyInjection` и `Extensions.Diagnostics` пока содержат каркасы. Проверяй их фактическое состояние перед использованием; не описывай запланированные методы как существующие.

- Не добавляй в Core или Abstractions зависимости от Npgsql, ORM, `ILogger`, DI, OpenTelemetry и конкретных хранилищ.
- Пользовательские удобные методы размещай в фасаде или extension-классе соответствующего адаптера. Не дублируй execution flow в адаптерах.
- EF-адаптер не должен зависеть от `BatchFlow.Postgres` или навязывать EF-провайдер. `EfCoreBatchSource` требует фабрику и освобождает контекст на каждую порцию до выдачи данных. Старый `EntityFrameworkCoreBatchSourceBase` сохраняет lifetime на перечисление и поддержку внешнего контекста. Контракты описаны в `docs/10-entity-framework-core.md` и `docs/11-ef-core-source.md`.
- Для готового EF-source обязательны стабильная уникальная сортировка, строгий предикат продолжения и согласованный сравниватель checkpoint. Не заменяй keyset на offset, не добавляй скрытую клиентскую пагинацию или отключение проверки порядка. Порция читает один дополнительный элемент для проверки границы; checkpoint берется с последнего выданного, не дополнительного элемента.
- Сохраняй разделение контрактов, runtime, fluent API и инфраструктуры. Новую абстракцию или проект вводи под конкретную ответственность и сценарий.
- По умолчанию оставляй реализацию `internal`. Новый публичный тип, virtual-метод или изменение сигнатуры рассматривай как изменение API библиотеки.

## Проектирование .NET-библиотек

- Используй необходимые паттерны и принятые практики разработки .NET-библиотек, выбирая решение под конкретный сценарий. Соблюдай SOLID, разделение ответственности и минимальность публичного API; обосновывай дополнительную сложность практической пользой.
- Развивай существующие паттерны последовательно: Builder для сборки задачи, Strategy для политик ошибок, Adapter для инфраструктуры, Observer для событий. Новый паттерн вводи, когда он решает определенную проблему расширения, сопровождения или тестирования.
- Предпочитай композицию. Наследование и виртуальные методы используй для осмысленных точек расширения с описанным контрактом, а не только ради доступа из теста.
- Делай контракты явными: nullable-семантика, потокобезопасность, владение ресурсами, отмена, исключения и гарантии выполнения должны быть понятны пользователю библиотеки.
- Сохраняй совместимость публичного API и поведения. Изменение контракта, значения по умолчанию или формата сохраненного checkpoint сопровождай оценкой влияния на потребителей и необходимой документацией миграции.
- Не используй service locator и скрытые изменяемые глобальные зависимости. Передавай зависимости явно; разделяй неизменяемую конфигурацию и состояние отдельного запуска.
- Проверяй эффективность на горячих участках: избегай повторного формирования неизменных данных, лишних аллокаций и блокировок. Подтверждай заявленное ускорение измерениями, сохраняя корректность и читаемость.

## Стиль C#

- Используй file-scoped namespaces, четыре пробела для отступов и фигурные скобки на отдельных строках.
- Имена типов, методов и свойств - `PascalCase`, параметров и локальных переменных - `camelCase`, приватных полей - `_camelCase`.
- Интерфейсы называй с префиксом `I`, асинхронные методы - с суффиксом `Async`. Для основных generic-параметров сохраняй `TItem` и `TCheckpoint`.
- Обычно размещай один основной тип в одноименном файле. Маленькие внутренние типы, обслуживающие один алгоритм, могут оставаться рядом с ним по существующему образцу.
- Для описаний, контекстов и результатов предпочитай records с `required` и `init`; для изменяемого runtime-состояния - отдельный класс. Не принимай поверхностную неизменяемость record за неизменяемость его коллекций и зависимостей.
- Конечные реализации делай `sealed`, если расширение наследованием не является частью контракта. Существующие точки расширения сохраняй.
- Проверяй аргументы в начале метода. Используй `ThrowIfNull`, `ThrowIfNullOrWhiteSpace` и проверки диапазонов; возвращай понятную ошибку с корректным именем аргумента.
- Простые выражения можно оформлять через `=>`. Сложные ветки и последовательности действий записывай обычными блоками.
- В объемных `switch` оборачивай тело каждого `case` в отдельные фигурные скобки, как в обработке `FailureAction`.
- Предпочитай циклы с понятным условием продолжения вместо `while (true)`. Не вводи `goto` и не маскируй бесконечный цикл фиктивным флагом, если можно выразить алгоритм яснее.
- Выноси крупную ветку обработки ошибки или чтение одной порции в осмысленный приватный метод. Основной метод должен оставлять видимой последовательность действий.
- Сохраняй оформление соседнего кода. Не смешивай функциональную правку с массовой перестановкой `using`, переименованиями и форматированием несвязанных файлов.

## SQL и строки запросов

- SQL, принадлежащий библиотеке, размещай в отдельных `internal static` классах с именованными `const string` запросами или шаблонами. Группируй их по ответственности, как `PostgresCheckpointQueries`, а не в одном общем классе всех строк проекта.
- Если запрос содержит настраиваемые имена схемы или таблицы, формируй окончательный текст один раз на экземпляр адаптера и сохраняй в `readonly` полях. Не повторяй интерполяцию, конкатенацию, `Replace` или `string.Format` при каждом чтении и сохранении.
- Подставляй в SQL-шаблон только проверенные и экранированные идентификаторы. Значения checkpoint, идентификаторы записей и остальные данные передавай через SQL-параметры.
- Пользовательский SQL из options сохраняй как пользовательскую конфигурацию. Не переноси его в глобальные константы библиотеки и не создавай неограниченный статический кеш запросов для разных конфигураций.
- Переиспользуй неизменяемый текст запроса, но не разделяй изменяемые `NpgsqlCommand`, reader или параметры между конкурентными операциями.
- Помни, что обычные строковые литералы уже переиспользуются средой выполнения. Вынос в константы упорядочивает SQL; устранение повторного формирования динамического текста дает отдельное уменьшение аллокаций. Это не эквивалентно подготовке запроса на стороне PostgreSQL.

## Язык и документация

- Общайся и пиши документацию проекта по-русски. Идентификаторы C#, имена API и названия технологий оставляй на английском.
- XML-комментарии пиши полностью на русском, без дублирования английского перевода.
- Документируй публичные типы и члены: объясняй смысл, ограничения, результат, существенные исключения и владение ресурсами. Используй `summary`, `param`, `typeparam`, `returns`, `remarks`, `exception` там, где они добавляют полезную информацию.
- Для реализации неизмененного контракта допустим `inheritdoc`. Дополнительные ограничения конкретного адаптера описывай явно.
- Обычные комментарии добавляй для нетривиальных причин и инвариантов; не пересказывай очевидные действия кода.
- При изменении поведения обновляй соответствующий документ в `docs`, а при изменении основного сценария - README. Примеры должны использовать существующий API и согласованные типы checkpoint.

## Асинхронность и ресурсы

- Сохраняй `ValueTask` и `IAsyncEnumerable` в существующих контрактах. Не меняй их на `Task` или синхронное перечисление без причины и проверки совместимости.
- Передавай `CancellationToken` последним параметром во все поддерживающие его операции. В асинхронных итераторах учитывай `EnumeratorCancellation`.
- Не блокируй асинхронный код через `.Result`, `.Wait()` или синхронные ожидания. Не используй `async void`, кроме требующих этого обработчиков событий.
- Не добавляй `Task.Run` автоматически вокруг I/O. Изменение модели выполнения CPU-нагрузки должно быть явным решением.
- Используй `using` / `await using`; учитывай исключение, отмену, ранний выход и неудачное открытие ресурса. Владение переданным соединением должно быть явно определено.
- Не разделяй одно активное Npgsql-соединение, `DbContext` или обычную изменяемую коллекцию между конкурентными handlers без предусмотренной синхронизации.
- При остановке параллельного алгоритма различай сигнал отмены и фактическое завершение задач. Первичная ошибка не должна теряться из-за вторичных ошибок остановки или диагностики.
- В репозитории `ConfigureAwait(false)` используется неоднородно. Не меняй все ожидания механически; следуй локальному стилю и отдельно оценивай контекст библиотечного кода.

## Инварианты выполнения

Это правила, которые нужно учитывать при развитии и тестировании runtime. Исторические дефекты не считай текущими без проверки кода и документа с актуальным статусом исправлений.

- Builder возвращает новое состояние. `ProcessEach` / `ProcessBatch` настраивают обработчик, `Build` создает описание, `Run...` выполняет задачу.
- В item-режиме DOP ограничивает элементы внутри одного пакета, в batch-режиме - разные пакеты. Не меняй эту семантику неявно.
- Source возвращает непустые пакеты, завершает последовательность при отсутствии данных и не изменяет уже выданные коллекции.
- Поддержка resume означает фактический учет `ResumeFrom`, а не только наличие типа checkpoint.
- Checkpoint продвигается по непрерывной подтвержденной последовательности. Поздний пакет не позволяет перескочить через незавершенный ранний.
- `Skip` - окончательный исход, допускающий продвижение checkpoint. Повтор после сбоя может затронуть уже выполненные внешние операции; exactly-once не обещается.
- Retry обработчика не означает retry source, сохранения checkpoint или observer. Изменение этих границ требует отдельного решения и тестов.
- Проверяй итоговый `summary.Status`, а не только отсутствие исключения. Сохраняй различие ошибок конфигурации, обработки, отмены и конкуренции checkpoint.
- Оптимистичная конкуренция checkpoint не является блокировкой одновременных запусков задачи.
- Ограничение входного channel не доказывает ограниченность памяти всего pipeline. Учитывай уведомления, ожидающие коммита пакеты и накопление диагностики.
- Сохраняй общий лимит пакетов от резервирования перед чтением до подтверждения. Не освобождай место при одном лишь завершении out-of-order пакета.
- Engine ожидает producer и всех workers перед возвратом. После проверки конфигурации внешняя отмена возвращается как Cancelled в summary; финальные observers не меняют выбранный исход.
- Retry и skip должны оставаться наблюдаемыми без накопления истории всех ошибок в runtime. Skip-событие не равнозначно сохраненному checkpoint.

## Тесты и проверка изменений

- Используй существующие xUnit и FluentAssertions; не добавляй второй тестовый стек без необходимости.
- Runtime, builder и logging проверяются в `BatchFlow.Core.Tests`; PostgreSQL-адаптер - в `BatchFlow.Postgres.Tests`; EF Core - в `BatchFlow.EntityFrameworkCore.Tests`. Переиспользуй doubles из `BatchFlow.Testing`. SQLite-тесты EF запускаются без внешней БД и не заменяют проверки других провайдеров; полный пример находится в `samples/BatchFlow.EntityFrameworkCore.Sample`.
- Для новых тестов следуй именованию соседнего класса. Не переименовывай старые тесты только ради унификации.
- Изменение поведения сопровождай тестом наблюдаемого результата; исправление дефекта - регрессионным сценарием. Проверяй существенные границы, а не зеркальное повторение реализации.
- Для конкурентных тестов используй `TaskCompletionSource` с `RunContinuationsAsynchronously`, управляемые барьеры и ограниченные ожидания. Не полагайся на произвольный `Sleep` как доказательство порядка выполнения.
- Для изменений checkpoint/parallel flow проверяй завершение не по порядку, сбой worker/source/store, отмену, границу коммита и завершение фоновых задач в относящихся к задаче сценариях.
- Fake reader не подтверждает работу SQL и lifetime настоящего подключения. Отдельно указывай, если интеграционная проверка PostgreSQL не выполнялась.
- Интеграционные PostgreSQL-тесты запускай через BATCHFLOW_POSTGRES_TESTS только на отдельной БД с суффиксом _tests. Используй уникальную схему fixture; не очищай чужие таблицы. Без подключения тесты должны явно пропускаться, а при неверном подключении - падать.
- Оптимизацию производительности подтверждай измерением. Разделяй подтвержденный bottleneck, вывод из структуры кода и предположение.

Команды запускай из корня репозитория, выбирая объем проверки по изменению:

```sh
dotnet restore BatchFlow.sln
dotnet build BatchFlow.sln --no-restore
dotnet test tests/BatchFlow.Core.Tests/BatchFlow.Core.Tests.csproj --no-restore
dotnet test tests/BatchFlow.Postgres.Tests/BatchFlow.Postgres.Tests.csproj --no-restore
dotnet test tests/BatchFlow.EntityFrameworkCore.Tests/BatchFlow.EntityFrameworkCore.Tests.csproj --no-restore
dotnet test BatchFlow.sln --no-restore
```

Restore нужен при отсутствии восстановленных зависимостей или изменении проектов/пакетов. После изменения кода выполни подходящие тесты и сборку затронутых проектов; при изменении общих контрактов или runtime проверь весь solution. Для чисто текстовой правки достаточно проверить содержание, ссылки и формат; измененные C#-примеры проверяй на компиляцию, а исполняемые сценарии - по возможности запуском.

## Порядок работы

- Если задача находится на стадии обсуждения или груминга, сначала проработай решение; не считай обсуждение разрешением менять код. Явный запрос на реализацию выполняй до проверки результата.
- Не перезаписывай и не откатывай чужие незакоммиченные изменения. Учитывай текущее рабочее дерево.
- Держи изменения в рамках задачи. Найденные несвязанные дефекты фиксируй отдельно, не добавляя скрытый рефакторинг.
- В итоговом сообщении кратко укажи, что изменено, чем проверено и какие существенные ограничения остались. Не называй непроверенное поведение гарантией или готовностью к промышленной эксплуатации.
